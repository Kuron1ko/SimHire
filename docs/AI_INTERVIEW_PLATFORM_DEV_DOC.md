# SimHire AI 面试平台总览文档

本文档是 SimHire 项目的稳定总览文档，供所有后续 agent 在开始任务前阅读。

本文档不记录每日进度，也不承担具体开发任务拆分。它只说明项目目标、阶段边界、协作规则、文档制度和 agent 如何判断当前进度。

## 1. 项目定位

SimHire 来自 `12.pptx` 中的 AI 面试模拟系统设想，目标是为在校学生、求职新人和需要高频面试训练的人群提供一个可练习、可评分、可复盘的 AI 面试平台。

长期目标是逐步从最小 Web 平台演进为接近真实线上面试的多模态模拟系统。项目不一次性追求完整形态，而是按阶段交付可验证能力。

核心用户价值：

1. 用户可以低成本反复进行模拟面试。
2. 用户可以获得结构化评价，而不是只得到泛泛建议。
3. 用户可以逐步获得更接近真人面试的语音、互动和视频体验。

## 2. 大阶段划分

项目分为四个大阶段。

### Phase 1 MVP：搭建最小平台

目标是跑通最小闭环：前端界面、面试会话、语音输入输出、文本问答、结束面试、评价报告。

阶段结果应该证明平台可用，而不是证明所有长期能力都已存在。

当前 Phase 1 已完成，可以作为后续阶段的稳定底座。

### Phase 2 Realtime：即时性互动

目标是把当前回合式“一问一答”升级为更像语音聊天的互动体验。

本阶段关注：

1. 用户长时间沉默时，面试官主动催促、安抚或复述问题。
2. 用户答非所问、乱答或明显不认真时，面试官提醒回到面试。
3. 用户提到项目亮点、数字结果、关键技术或高价值经历时，面试官能追问，必要时适度打断。
4. 前端通过实时 transcript、语音活动检测和 WebSocket 事件流让交互更即时。

本阶段不追求完美真人抢话，也不做视频数字人。

### Phase 3 Intent & Voice：意图编排与情绪化语音合成

目标是在稳定实时互动之上，引入更明确的面试官意图编排和更自然的语音表现。

本阶段关注：

1. 面试官行为不只由简单规则触发，而由意图、阶段、压力强度和候选人状态共同决定。
2. 面试官语音不再只是浏览器电子音，而能根据追问、鼓励、提醒、压力测试等意图产生不同语气。
3. LLM、TTS、prompt builder 和行为编排器通过 adapter 与业务逻辑隔离。

### Phase 4 Video Simulation：视频合成与线上面试模拟

目标是在语音互动和意图编排稳定后，探索视频合成能力，尽可能模拟线上面试。

本阶段非常困难，不保证一定成功。它应该先做技术验证，再决定是否进入产品化。

本阶段关注：

1. 虚拟面试官画面或视频形象。
2. 表情、口型、姿态与语音节奏同步。
3. 摄像头输入、复盘时间线和多模态评价。

## 3. AI 调用路径原则

当前仓库还没有真实调用外部 AI 模型。Phase 1 的提问和评价使用确定性 mock 与规则评分。

后续接入真实模型时，必须遵守以下调用路径：

```text
Browser
  -> apps/web/src/services/apiClient.ts
  -> FastAPI /api/*
  -> InterviewOrchestrator / EvaluationService / RealtimeInterviewService
  -> QuestionAgent / BehaviorOrchestrator / EvaluationService
  -> LLMProvider 或 RealtimeProvider
  -> OpenAI-compatible API
```

原则：

1. 前端永远只调用 SimHire 后端，不直接调用 OpenAI 或任何模型供应商。
2. 模型 key 只存在后端环境变量或服务端密钥系统中，不能进入浏览器代码、前端 env 或生成产物。
3. 所有真实模型 provider 必须至少支持两个核心参数：`base_url` 和 `api_key`。
4. 项目环境变量命名为 `LLM_BASE_URL` 和 `LLM_API_KEY`；provider 内部可映射为 `base_url` 和 `api_key`。
5. 真实 provider 失败、缺少 key 或网络不可用时，必须能回退到 mock provider 或给出可恢复错误，不能破坏 MVP 闭环。
6. 不允许把供应商 SDK 调用直接散落在路由、orchestrator 或页面代码中；必须通过 provider adapter。

## 4. 文档体系

文档分为四类。

### 总览文档

路径：`docs/AI_INTERVIEW_PLATFORM_DEV_DOC.md`

作用：

1. 说明项目总目标和四个大阶段。
2. 说明 agent 工作制度。
3. 说明阶段起始文档的读写规范。
4. 说明如何得知当前进度。

限制：

1. 总览文档应保持稳定。
2. 不应把日常进度、某个 subagent 的临时结论、具体 bug 列表写进总览文档。
3. 只有当项目阶段制度、长期架构原则或协作规则变化时，才修改总览文档。

### 阶段起始文档

路径：`docs/phases/PHASE_*_START.md`

作用：

1. 记录某一阶段开始时的代码基线。
2. 定义该阶段目标、非目标、推荐结构、接口契约、subagent 拆分、验收标准和回归命令。
3. 作为该阶段所有 subagent 的主要任务依据。

读写规则：

1. 每个 agent 开始任务前，先读总览文档，再读操作者或任务提示指定的阶段起始文档。
2. subagent 不应随意改写整个阶段起始文档。
3. 如果 subagent 完成了阶段内一部分任务，应在自己的最终回复中说明变更和验证结果，由阶段负责人决定是否同步进阶段文档。
4. 当一个大阶段收尾时，负责收尾的 agent 应根据真实代码状态，为下一个大阶段更新或重写起始文档。
5. 阶段起始文档必须以当前仓库真实代码为准，不能只复述理想设计。

### 操作者文档

路径：`docs/OPERATOR_GUIDE.md`

作用：

1. 给项目操作者阅读，说明如何使用 agent 推进项目。
2. 简要说明项目阶段和当前所处位置。
3. 由操作者维护当前阶段、任务安排和人工判断。

限制：

1. 该文档是 human-owned 文档。
2. AI agent 默认不得读取、引用、修改 `docs/OPERATOR_GUIDE.md`。
3. 只有当操作者在当前对话中明确要求 AI 访问或修改它时，AI 才能操作。
4. agent 需要判断当前进度时，应阅读阶段起始文档、检查代码和测试，或者询问操作者，而不是打开操作者文档。

### 调试者文档

路径：`docs/DEBUGGER_GUIDE.md`

作用：

1. 告诉调试者如何在本地安装依赖、启动后端、启动前端、打开页面和运行回归命令。
2. 记录当前项目的端口、环境变量、常见错误和排查方法。
3. 帮助后续 agent 或人工调试者快速复现当前可运行状态。

维护规则：

1. 该文档由 AI agent 更新。
2. 当启动方式、端口、环境变量、依赖安装方式、回归命令或常见问题发生变化时，相关 agent 必须同步更新该文档。
3. 调试者文档可以随着代码进度变化；它不需要像总览文档一样保持长期稳定。
4. 该文档只写运行和调试方法，不写阶段规划和产品决策。

## 5. Agent 工作制度

每个 agent 开始工作前必须执行以下阅读顺序：

1. 阅读本总览文档。
2. 阅读当前任务指定的阶段起始文档。
3. 如果任务涉及运行、调试、验收或本地复现，阅读 `docs/DEBUGGER_GUIDE.md`。
4. 检查与自己任务相关的代码、测试和生成文件。
5. 如果文档与代码冲突，以代码和测试的真实状态为准，并在最终回复中指出文档需要同步。

每个 agent 的工作边界：

1. 只实现当前任务指定范围。
2. 不抢先实现后续大阶段能力。
3. 不删除已有稳定 fallback。
4. 不手工修改生成产物，除非该生成产物本身就是任务目标且已说明原因。
5. 修改公共 schema、API path、评分维度、状态机时，必须同步测试和生成类型。
6. 引入新依赖时，要说明原因，并优先选择成熟、轻量、维护活跃的库。

每个 agent 完成任务后必须交代：

1. 改动了哪些文件。
2. 新增或调整了哪些接口。
3. 运行了哪些验证命令。
4. 哪些能力尚未覆盖。
5. 是否需要后续 agent 继续处理。

## 6. 如何判断当前进度

总览文档不随进度变化，因此 agent 不能从本文判断最新实现状态。

判断当前进度的推荐顺序：

1. 查看操作者或任务 prompt 指定的阶段。
2. 阅读对应阶段起始文档，例如 `docs/phases/PHASE_2_REALTIME_START.md`。
3. 查看代码目录、测试文件、生成类型和最近的接口契约。
4. 运行该阶段文档列出的回归命令。
5. 如果阶段文档与代码不一致，以代码和测试为准，并在最终回复中建议更新阶段文档。
6. 如果仍无法判断当前阶段，应向操作者询问，不要自行打开 human-owned 操作者文档。
